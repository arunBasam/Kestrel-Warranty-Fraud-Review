# Kestrel Home — Warranty Claim Review (Variant C)

## Setup (clean machine)

```
pip install -r requirements.txt
python3 train_model.py          # builds model.joblib, predictions.csv, validation_metrics.json
python3 baseline_comparison.py  # random/highest-amount/new-partner/rule-only/model comparison -> baseline_metrics.json
python3 bootstrap_validation.py # confidence intervals (AUC, precision@40, net Rs) -> bootstrap_metrics.json
python3 validate.py             # leakage/integrity/reproducibility audit
python3 app.py                  # starts the service at http://127.0.0.1:5000
```

Open `http://127.0.0.1:5000/` in a browser for the one-screen UI, or call the
API directly:

```
curl -X POST http://127.0.0.1:5000/score -H 'Content-Type: application/json' -d '{
  "claim_id":"WC900001","submitted_at":"2026-08-15 10:00","partner_id":"SP3219",
  "sku":"KH-MG-03","product_serial":"KH395147108","days_since_purchase":120,
  "claim_amount_inr":1850,"photo_attached":"N","partner_inspected":"N",
  "customer_prior_claims":2
}'
```

No paid API key is used anywhere in this project. If `model.joblib` hasn't
been generated yet (i.e. you run `app.py` before `train_model.py`), the
service still starts; `/score` returns a clear `503` telling you to run
`train_model.py` first, rather than crashing.

## Files

- `train_model.py` — builds features, validates honestly, trains the final model, writes `predictions.csv`.
- `features.py` — feature engineering shared by training and the live service, so a claim is featurized identically either way.
- `explain.py` — turns a score into plain-English reasons, using the model's own coefficients (no LLM, no external API).
- `app.py` — the Flask service (`/score` endpoint + one-screen UI).
- `predictions.csv` — one score per `claim_id` in `test_unlabelled.csv`, matching `sample_submission.csv`'s shape.
- `model.joblib` — the fitted pipeline + calibrator (generated by `train_model.py`, not hand-edited).
- `validate.py` — leakage/integrity tests, including an adversarial check, plus a live re-derivation of the rule-vs-model comparison. Run after `train_model.py`.
- `validation_metrics.json` — point-estimate metrics (AUC, precision@40, walk-forward table, economics sweep), reproducible by re-running `train_model.py`.
- `bootstrap_validation.py` — the 3,000-resample bootstrap behind every confidence interval quoted in `FINAL_VALIDATION_REPORT.md`. Writes `bootstrap_metrics.json`. Run separately from `train_model.py` (not folded in, so each script stays fast and single-purpose) — run this before trusting any CI number in the docs.
- `bootstrap_metrics.json` — output of the above; the CIs in every `.md` file are copied from this file, not hand-typed.
- `FINAL_VALIDATION_REPORT.md` — the full validation writeup (dataset integrity, leakage tests, walk-forward validation, baseline/rule comparison, calibration, bootstrap uncertainty, economics, final recommendation).

## What this deliberately does *not* do

- **It does not optimize for "97% accuracy."** Fraud is ~1.3% of labeled claims historically; a model that predicts "not fraud" on every single claim already scores **98.7% accuracy** while catching zero fraud — and in June 2026 alone (post-auto-approval-change), the same do-nothing model would score only 96.9%, *below* the board's bar. Accuracy is unreliable in both directions here. See `memo-to-ritu.md` and `decision-log.md` for the metric actually used instead (rupees of fraud stopped per claim reviewed, at the investigation desk's real capacity of 40/month).
- **It does not correct the legacy label contamination.** Before 1 Oct 2025, the old Zoho system couldn't store a blank `is_fraud`, so undecided legacy cases were coded as `0`. Some unknown fraction of legacy "not fraud" labels are therefore "never investigated," not "confirmed genuine." This can't be fixed from the export alone; it's disclosed, not patched.
- **It does not auto-reject anything.** The service returns a score and a review recommendation for a capacity-constrained investigation queue, not an auto-decision. At current precision (~22.5% at the top of the queue), most flagged claims are still genuine.
- **It is not a random forest / neural net / LLM-based classifier.** A plain logistic regression outperforms a gradient-boosted model specifically on the one validation window that matches test's post-policy-change distribution — see `decision-log.md` for the walk-forward comparison that decided this.

## Known limitations

- The labeled validation window with the auto-approval regime is short (June 2026 only, 22 fraud cases) — real, but noisy. Precision/economics estimates should be treated as directional until more months of post-change labels accumulate.
- `partner_type` "unrecorded" fallback: if a live `/score` request references a `partner_id` not in `partners.csv` (e.g. a brand-new partner not yet in the roster), features derived from partner history degrade gracefully rather than erroring, but the score is less trustworthy for that case.
